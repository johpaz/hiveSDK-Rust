# Entrada acumulada, framing y ventana combinada

Se conserva `neutral_json` por compatibilidad y se añaden `openai_chat_json`, `anthropic_messages_json` y `gemini_generate_content_json`. Cada perfil serializa la entrada mediante el mismo constructor del adaptador, retirando parámetros de salida. La codificación BPE sigue siendo explícita, también en Anthropic/Gemini: es una estimación del JSON, no su tokenizer privado ni un conteo facturable. Se descarta inferir perfiles por nombre del modelo y consultar endpoints de conteo porque añaden ambigüedad o solicitudes auxiliares.

`input_token_budget.max_total_tokens` limita la entrada acumulada del turno. Antes de despachar se comprueba saldo contra la estimación; cada respuesta conocida carga el máximo entre estimación y uso de entrada reportado. Se conservan métricas separadas de estimación, carga preventiva y uso real. Ausencia de uso bajo este límite detiene la continuación. El estado pendiente conserva la reserva y no puede reejecutarse sin reconciliar. Preflight no acumula cobros; reanudar no reinicia saldo. Empezar un turno nuevo sigue reiniciando su presupuesto local; los límites del Objective siguen siendo globales.

`context_window_tokens` exige un cap explícito de salida en LoopPolicy. La selección debe alojar entrada estimada + cap reservado; no reduce la salida de forma silenciosa. Con drop_oldest_turns se eliminan turnos completos antiguos antes de parar. Sistema y turno activo se conservan, incluidos pares tool/resultado. La entrada acumulada también puede reducirse con esa selección; si ni la selección mínima cabe, se detiene antes de reservar otra salida o consultar el modelo.

Pruebas: referencia contra JSON real de los adaptadores y BPE; límites exactos y un token menos; límites simultáneos bytes/entrada/ventana; preflight repetido, uso mayor al estimado, uso ausente, tool conocida antes de agotarse el saldo, checkpoint y reapertura; paridad de ambos bindings. No se usarán modelos de pago ni se afirmará un techo monetario.
